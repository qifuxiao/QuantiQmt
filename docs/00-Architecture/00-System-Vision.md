# 系统愿景

> Status: Proposed  
> Updated: 2026-08-28

## 定位

QuantiQmt 是 Python 实现的、面向 MiniQMT 起步并可扩展至多 Broker 的企业级量化交易系统。系统负责行情接入、策略运行、统一风控、订单管理、执行、账户持仓、对账恢复、审计和运维。

首个可运行里程碑必须连接 Mini QMT 模拟账号并完成受控端到端闭环；Broker Simulator
不能替代该验收。该交付优先级不得削弱 OrderIntent、OMS、Risk、Execution、UNKNOWN、
恢复屏障、持久化和审计不变量，真实资金交易仍需独立准入。

它不以 Notebook、因子研究或快速拼装策略为核心目标。研究工具可以接入，但不得削弱生产交易的控制边界。

## 质量目标

| 维度 | 目标 | 验收方式 |
|---|---|---|
| 实时性 | 热路径无数据库同步 I/O；避免无界队列和重复计算 | 分阶段延迟直方图与压测 |
| 稳定性 | QMT、Redis、数据库单点异常不导致无条件进程退出或失控下单 | 故障注入 |
| 一致性 | 订单、成交、持仓、资金均有权威来源、派生规则和对账流程 | 重启及差异演练 |
| 风控 | 策略无下单能力；所有新单和改单经过统一风险决策 | 权限与集成测试 |
| 容错 | 超时、断连、乱序、重复、脏数据有确定处理策略 | 故障矩阵测试 |
| 可观测 | 可通过 correlation_id 还原一次交易的完整链路 | 追踪与审计查询 |
| 一致复用 | Live 与 Backtest 共享领域模型和交易语义 | 契约测试 |

## 初始 SLO（待基准测试确认）

- 系统自身 `MarketEvent → OrderCommand` 的 P99 目标小于 20 ms，不含 Broker/网络耗时。
- 交易核心在额定容量下不允许无界积压；达到高水位时必须降级或拒绝新意图。
- 交易日内核心服务可用性目标 99.9%；严重故障进入安全模式，而不是盲目重试。
- 订单恢复 RTO 目标 60 秒，审计事件 RPO 目标 0；具体能力取决于 Broker 查询接口。
- 每日开盘前必须完成 Broker、本地账本和持仓资金基线核对。

## 非目标

- 不承诺微秒级高频交易；Python/GIL、MiniQMT 和通用网络不是该目标的技术基础。
- 不宣称端到端 Exactly Once；采用 At-Least-Once、幂等键、单写者和对账获得业务正确性。
- 不保证回测结果与实盘逐笔相同；保证领域规则和订单语义一致，并显式建模现实差异。
